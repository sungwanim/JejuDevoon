# 제주 농업 데이터 분석 Agent

## Problem Statement

제주 농업인과 도민은 "내 밭에 무엇을 심거나 늘리면 좋을지", "요즘 이 작목 시세가 어떤지"를 데이터로 판단하고 싶다. 하지만 필요한 데이터는 제주데이터허브 API, 허브 CSV, 기상청 관측자료, 국토지리정보원 DEM처럼 여러 곳에 흩어져 있고, 인코딩·단위·결측 표기·공간 단위가 제각각이다. IT 비전문가는 어떤 데이터가 있는지, 어떤 데이터가 자기 질문에 맞는지, 어떻게 열고 계산하는지 알기 어렵다.

제주는 해안에서 중산간까지 고도 차가 커서 같은 읍면 안에서도 겨울 최저기온이 몇 도씩 다르다. 그런데 사람들은 보통 가장 가까운 관측소 값이나 감에 의존해 판단한다. 시도 단위 통계로 내 밭을 판단하는 것처럼, 질문에 맞지 않는 해상도의 데이터를 쓰는 실수도 흔하다.

제주빅데이터센터는 이런 도민이 센터 PC에서 직접 실행해, 데이터 탐색부터 분석 결과까지 얻을 수 있는 서비스를 원한다. 결과는 근거와 한계가 분명해야 하고, 코드와 매뉴얼로 재현할 수 있어야 한다.

## Solution

로컬 웹앱이다. 사용자는 지도에서 위치를 클릭하고 자연어로 질문한다. Agent는 다음을 스스로 수행한다.

1. 요청을 규격화된 계획으로 바꾼다. 필수 정보가 빠졌으면 한 번 되묻고, 제주 농업·기후·시장 데이터 분석과 무관하면 정중히 불가라고 말한다.
2. 데이터 카탈로그에서 쓸 데이터를 고르고, 쓰지 않는 데이터와 그 이유를 함께 남긴다. 쓸 데이터가 없으면 불가라고 말하고 어떤 데이터가 있어야 하는지 안내한다.
3. 고른 데이터를 불러와 요약 정보(Profile)를 만든다.
4. 질문을 순서 있는 작업 목록으로 나누고, 작업마다 기존 분석 모듈을 재사용·수정하거나 새 분석 코드를 만든다. LLM은 원본 데이터를 통째로 보지 않고 스키마·Profile·샘플 값만 보고 코드를 짠다. 코드는 격리 실행으로 mock 데이터와 실데이터에서 검증되고, 검증을 통과한 코드는 다음 사용자를 위해 저장된다.
5. 중간산출물로 최종 HTML을 만든다. 공간 정보가 필요하면 지도 중심 HTML, 보고서를 원하면 보고서형 HTML, 쉽게 설명해 달라면 흐름도·그림 중심 HTML이다. 모든 산출물에는 사용·제외한 데이터와 이유, 분석 과정, 근거와 한계가 들어간다. 본문 숫자는 모두 중간산출물에서 나온 값이다.

수익을 보장하지 않는다. "재배 적합도(기후·고도 조건)와 시장 신호(가격 추세·변동성·공급 추세)"를 근거와 함께 보여주는 의사결정 보조 도구다.

## Implementation Decisions

### 기술 환경

- 백엔드는 Python + FastAPI, 프론트엔드는 Vite + React, 지도는 react-leaflet. 로컬 웹앱으로 센터 PC(i7-8700 / GTX1060 / 32GB, 인터넷 가능)에서 실행한다.
- LLM은 OpenAI GPT-4o 하나. 구조화가 필요한 모든 단계는 Structured Outputs(JSON 스키마)로 호출한다. `temperature=0`, `seed` 고정.
- Agent 프레임워크(LangGraph 등)는 쓰지 않는다. 하나의 실행 상태 객체를 단계 함수들이 차례로 갱신하는 Python 상태 머신으로 구현한다.
- 비밀값(OpenAI 키, 허브 프로젝트키, 공공데이터포털 serviceKey)은 환경변수 파일에서만 읽는다. 코드·산출물·실행 기록·생성 코드 실행 환경에 넣지 않는다.

### 원칙

- LLM은 선택하고 설계하고 설명한다. 숫자는 코드가 만든다.
- LLM은 원본 행을 통째로 보지 않는다. 스키마, Profile, 컬럼당 샘플 값 3~5개만 본다.
- 할 수 있는 범위는 질문 유형(intent) 목록이 아니라 카탈로그의 데이터와 도구가 정한다. 질문 유형으로 경로를 고정하지 않는다. 도메인 경계는 "제주 농업·기후·시장 데이터 분석" 하나다.
- 할 수 없으면 할 수 없다고 말하고, 이유와 대안을 낸다.

### 모듈

**Agent Runner (주 진입점).** 입력은 사용자 요청 문장, 선택적 클릭 좌표, 선택적 이전 대화 상태(되묻기 이후). 출력은 실행 결과: 종료 상태, HTML 산출물(있을 때), 실행 기록. LLM 클라이언트와 데이터 소스 레지스트리를 주입받는다. 단계 순서: ① 요청 규격화 → ② 데이터 선택 → ③ 로드·Profile → ④ 분석(작업 목록, 작업별 모듈·코드·검증·저장) → ⑤ 렌더.

**종료 상태.** `answered`(모든 작업 성공), `partial`(일부 작업 실패·로드 실패·답할 수 없는 하위 질문 있음), `clarify`(필수 정보 부족, 질문 1개), `infeasible`(도메인 밖 또는 쓸 데이터 없음, 이유와 필요한 데이터 안내), `failed`(시스템 오류 또는 모든 작업 실패, 원인과 해결 방법).

**상한.** 작업별 코드 시도 2회(생성 + 수정), 실행당 LLM 호출 25회, 생성 코드 실행 작업당 60초, 실행 전체 5분. 넘으면 그때까지의 결과로 렌더한다. 수치는 초안이며 실측 후 조정한다.

**LLM 클라이언트 (교체 가능한 어댑터).** 스키마를 받아 구조화 응답을 돌려주는 호출과, 자유 텍스트 호출을 제공한다. 운영에서는 OpenAI, 테스트에서는 미리 정한 응답을 순서대로 돌려주는 가짜를 쓴다. 호출마다 모델·프롬프트 해시·토큰·시간을 실행 기록에 남긴다.

**데이터 소스 레지스트리 (교체 가능한 어댑터).** 카탈로그 id로 데이터를 불러온다. 운영에서는 라이브 API + 캐시, 테스트·재현에서는 스냅샷 파일을 쓴다.

**① 요청 규격화 (Request Planner).** LLM이 RequestPlan을 낸다. 필드: 정규화된 목표 한 문장, LLM이 직접 분해한 하위 질문 목록, 필요한 성격(지점 분석·시계열·공간 비교 여부), 위치(종류·위경도·텍스트), 작목, 기간, 원하는 스타일(보고서/쉽게), 빠진 필수 정보 목록, 도메인 안 여부와 이유, 보조 태그(경로 결정에 쓰지 않음, 검색·평가 분류용). 이어서 코드 규칙이 적용된다:
- 산출물 형식 결정: 지점 분석이나 공간 비교가 필요하면 무조건 `map`. 아니면 스타일에 따라 `report` 또는 `visual`.
- 빠진 필수 정보가 있으면 `clarify`.
- 도메인 밖이면 `infeasible`.
- 좌표가 제주 본섬 밖이거나 바다면 범위 밖 안내.
- 수익 보장 요청은 불가가 아니라 재구성 안내.

**② 데이터 선택 (Data Selector).** LLM에게는 카탈로그 요약(제목, 출처, 공간·시간 단위, 범위, 컬럼 이름·의미·단위)만 준다. 데이터셋 id는 스키마의 enum으로 제한해 존재하지 않는 id를 원천 차단한다. 출력 Selection: 실행 가능 여부, 선택 목록(id, 이유, 필요한 컬럼), 제외 목록(id, 이유 코드, 메모), 답할 수 없는 하위 질문과 이유, 불가 이유. 제외 이유 코드: 무관, 해상도 불일치, 지역 불일치, 기간 불일치, 컬럼 부족. 코드 규칙 필터: 지점 분석이 필요한데 지점·격자·관측소 단위 데이터가 하나도 없으면 불가. 시도 단위 데이터는 지점 분석에서 보조로만. 기간이 겹치지 않는 데이터 자동 제외. 카탈로그가 30개를 넘으면 상위 20개만 LLM에 보낸다.

**③ 로드·Profile (고정 도구 라이브러리).** 사람이 작성·테스트한 함수들로, Agent가 호출하고 생성 코드에서도 import해 쓴다. 기능: 파일/API 구분 로드, 인코딩 자동 판별(cp949/utf-8), API 페이지 처리, 캐시, Profile 생성(행 수, 인코딩, 컬럼별 타입·결측률·최소·최대·고유값 수·샘플 3~5개, 카탈로그의 의미·단위), 날짜·숫자 변환, 지역 필터, 기간 집계, 키 결합(결합률 보고), 지점 고도 조회. 로드에 실패한 데이터는 빼고 진행하며 종료 상태를 `partial`로 만든다.

**④ 분석.**
- 작업 목록: LLM이 하위 질문과 선택된 데이터로 순서 있는 작업 목록을 만든다. 각 작업은 "어떤 중간산출물을 어떤 데이터(또는 앞 작업의 중간산출물)로 만드는가"다. 재계획은 하지 않는다.
- 모듈 검색: 작업 설명의 임베딩 유사도와 필요한 역할(날짜, 가격, 품종 등)로 모듈 라이브러리에서 후보를 고른다. `verified`를 `auto`보다 우선한다.
- 결정: LLM이 재사용 / 수정 / 신규 중 하나를 고르고, 데이터 컬럼을 모듈의 입력 역할에 매핑한다.
- 중간산출물 설계: 각 작업이 만들 중간산출물의 id, 종류(표·지표·시계열·지리), 설명, 컬럼과 타입·단위를 먼저 정한다.
- 코드 계약: 생성 코드는 메타데이터(제목, 검색용 설명, 태그, 입력 역할, 파라미터, 출력 목록), 실행 함수(역할 이름으로 바뀐 입력 데이터프레임들과 파라미터를 받아 중간산출물 사전을 반환), 검증 함수(출력과 입력을 받아 문제 목록을 반환, 비면 통과)를 갖춘다. 입력 컬럼은 실행 직전에 역할 매핑으로 이름이 바뀌어 들어가므로, 같은 모듈을 컬럼 이름이 다른 데이터에 재사용할 수 있다.
- 검증 순서: 정적 검사(문법, import 허용 목록, 금지 호출) → mock 테스트(Profile로 가짜 데이터를 만들어 실행, 출력 스키마 일치와 검증 함수 통과) → 실데이터 실행 + 검증 함수 + 공통 검사(빈 결과·전부 결측 금지, 카탈로그 단위 기준 상식 범위). 첫 실패에서 중단한다. mock은 오류와 형식 불일치만 잡고 계산의 정확성은 못 잡는다는 점을 문서에 명시한다.
- 재시도: 최대 2회. 1차 실패를 코드로 분류한다. 컬럼·역할 불일치 → 코드가 아니라 역할 매핑을 다시. 형식 오류 → 해당 컬럼 샘플·Profile을 붙여 최소 수정. 금지 사항 → 허용 목록을 붙여 최소 수정. 시간 초과 → 벡터 연산·기간 축소 지시. 검증 실패 → 실패 항목과 출력 요약 통계를 붙여 최소 수정. 데이터 문제(필터 후 빈 데이터, 필요한 기간 없음) → 2차 없이 바로 작업 실패. 2차 코드가 1차와 같으면(공백·주석 제거 후 해시 비교) 실행하지 않고 작업 실패. 2차도 실패하면 작업 실패로 기록하고 다음 작업으로 간다.

**생성 코드 실행기 (보조 진입점).** 입력: 코드, 입력 데이터, 파라미터, (mock이면) Profile. 출력: 중간산출물, 검증 결과, 실패 분류, 실행 시간. 별도 프로세스, 제한시간, 작업 폴더 한정, 환경변수에서 비밀값 제거, 네트워크 차단, import 허용 목록(pandas, numpy, scipy, 표준 수학·통계·날짜, 고정 도구 라이브러리). 악의적 코드를 막는 보안 샌드박스가 아니라 LLM 실수를 막는 장치이며, 이 한계를 제출 문서에 적는다.

**모듈 라이브러리.** 검증을 통과한 코드를 모듈 id·버전별로 저장한다. 메타데이터: 제목, 검색용 설명, 태그, 입력 역할, 출력 스키마, 파라미터, 검증 기록(mock·실데이터 통과), 테스트한 데이터 id와 버전 해시, 생성 모델, 생성일, 원 요청 목표(개인정보 제거). 상태는 `verified`(사람 검토, 기본 탑재)와 `auto`(검증 통과 시 자동 저장). 데이터 버전 해시가 바뀌면 캐시된 결과는 버리고 코드는 재검증해서 쓴다. 대표 분석(품목별 가격 추세·변동성, 지점 기후 요약, 카탈로그 탐색 등)은 `verified` 모듈로 미리 탑재해 LLM 코드 생성 없이도 재현되게 한다.

**⑤ 렌더 (Renderer).** LLM이 ReportSpec을 낸다: 제목, 3문장 이내 요약, 섹션 목록(제목, 설명 문장, 블록 목록), 한계 목록. 블록 종류: 차트(중간산출물 id + 차트 종류), 지도(지리 중간산출물 id), 흐름도(Mermaid), 표(중간산출물 id), 강조 상자. LLM은 숫자를 직접 쓰지 않고 중간산출물을 참조한다. 숫자 근거 대조: 본문 숫자를 뽑아 중간산출물 값과 대조(반올림 허용), 근거 없는 숫자가 든 문장은 바로 제거. 형식별 템플릿으로 독립 HTML 한 파일을 만든다. `report`: 요약 → 방법 → 결과(표·차트) → 한계 → 출처. `visual`: 큰 결론 한 줄 → 흐름도 → 단순 차트 → 쉬운 말 설명. `map`: 지도 중심 + 요약·차트. 공통 섹션: 사용한 데이터 / 제외한 데이터와 이유, 분석 과정(모듈 id·버전), 근거와 한계, 데이터 출처·이용조건, 답하지 못한 부분과 이유. 차트·흐름도·지도 라이브러리는 CDN으로 로드한다(Chart.js, Mermaid, Leaflet).

**실행 기록 (trace).** 단계별 입력·출력, LLM 호출 정보, 선택·제외 결정, 작업별 코드 시도·실패 분류, 상태 전이를 실행마다 저장한다. 화면의 "탐색 로그"와 제출 문서의 실행 결과 자료로 쓴다.

**HTTP API.** 실행 시작(요청 문장 + 좌표 + 대화 id), 실행 상태·단계 진행 조회, 실행 결과(HTML·실행 기록) 조회, 카탈로그 목록 조회.

**프론트엔드.** 채팅 입력, 제주 본섬 지도와 클릭 위치 표시, 단계 진행 표시, 실행 기록(사용·제외 데이터, 작업별 결과) 패널, 결과 HTML 보기와 저장, 되묻기 답변 이어 쓰기.

### 판단 주체 (제출 기획서의 "판단 및 자율 수행 범위")

- Agent(LLM)가 스스로 하는 것: 요청 의도 파악과 하위 질문 분해, 되묻기 판단, 데이터 선택과 제외 이유, 작업 목록 작성, 모듈 재사용·수정·신규 결정과 역할 매핑, 분석 코드 작성과 수정, 결과 구성과 설명.
- 규칙(코드)이 정하는 것: 산출물 형식, 도메인·범위 판정 보조, 해상도·지역·기간 적합성, 적합도 점수, 가격 추세·변동성 계산, 검증과 실패 분류, 숫자 근거 대조.
- 하지 않는 것: 수익 보장, 근거 없는 수치 생성, 출처 없는 재배 기준 사용.

## Testing Decisions

### 좋은 테스트의 기준

- 외부에서 보이는 동작만 검증한다: 종료 상태, 산출물 형식, 산출물에 들어간 섹션과 데이터 사용·제외 내역, 실행 기록에 남은 결정, 모듈 라이브러리의 저장·재사용 여부.
- 단계 함수 내부 구현, 프롬프트 문구, 중간 객체의 세부 필드 순서는 검증하지 않는다.
- LLM은 가짜 클라이언트로, 데이터는 스냅샷으로 고정해 테스트를 결정적으로 만든다.

### 테스트 경계

**주 경계: Agent Runner 하나.** 요청 문장 + 좌표(+ 대화 상태)를 넣고 실행 결과를 받는다. LLM 클라이언트와 데이터 소스 레지스트리만 교체한다. 이 경계에서 확인할 동작:
- 도메인 밖 요청 → `infeasible`
- 지점 분석이 필요한데 위치 없음 → `clarify`, 질문 1개. 이어서 위치를 주면 이전 계획과 합쳐 진행
- 쓸 데이터가 없는 요청 → `infeasible`과 필요한 데이터 안내
- 지점 질문에서 시도 단위 데이터는 제외 목록에 해상도 불일치로 남음
- 일부 하위 질문만 답할 수 있음 → `partial`과 답하지 못한 부분 표시
- 데이터 하나 로드 실패 → 나머지로 진행, `partial`
- 공간 정보가 필요한 요청 → `map` 형식, 스타일 요청과 무관하게
- 보고서 요청 → `report`, 쉬운 설명 요청 → `visual`
- 1차 코드 실패 후 2차 수정 성공 → 작업 성공, 실행 기록에 실패 분류와 2회 시도
- 2차 코드가 1차와 동일 → 실행하지 않고 작업 실패
- 데이터 문제로 분류된 실패 → 2차 없이 작업 실패
- 모든 작업 실패 → `failed`
- 검증을 통과한 신규 코드 → 모듈 라이브러리에 `auto`로 저장, 비슷한 두 번째 요청에서 재사용 후보로 선택되고 재검증됨
- 데이터 버전 해시 변경 → 캐시된 결과를 쓰지 않음
- 렌더 결과의 근거 없는 숫자 문장 → 제거됨
- 모든 산출물에 공통 섹션(사용·제외 데이터, 분석 과정, 근거와 한계, 출처) 포함
- 상한(LLM 호출 수, 전체 시간) 초과 → 그때까지의 결과로 렌더
- 제주 본섬 밖·바다 좌표 → 범위 밖 안내

**보조 경계: 생성 코드 실행기.** 코드와 입력을 넣고 결과를 받는다. 확인할 동작:
- 금지 import·금지 호출이 정적 검사에서 차단됨
- 제한시간 초과 시 강제 종료되고 시간 초과로 분류됨
- 출력이 설계한 중간산출물 스키마와 다르면 실패
- 검증 함수가 문제를 반환하면 실패와 그 내용이 전달됨
- 생성 코드 실행 환경에 비밀값 환경변수가 없음
- mock 데이터가 Profile의 타입·범위·결측률·샘플 값을 반영함
- 실패 분류(컬럼·역할 불일치, 형식 오류, 금지 사항, 시간 초과, 검증 실패, 데이터 문제)가 대표 오류에서 올바르게 나옴

**고정 도구 라이브러리**의 데이터 처리 규칙(cp949 판별, 문자열 숫자 변환, 이동평균의 0을 결측으로, DEM 바다 마스크, 범위 밖 좌표)은 주 경계 테스트의 스냅샷 데이터로 함께 확인한다. 별도 경계를 만들지 않는다.

### 평가 도구 (시험지)

- 주 경계를 그대로 쓰되 LLM만 실제 GPT-4o로 바꿔 질문 30~50개를 일괄 실행한다.
- 질문마다 정답 정보: 필요한 성격, 산출물 형식, 되묻기 여부, 도메인 판정, 반드시 포함/제외할 데이터, 불가 여부.
- 대표 질문 외에 처음 보는 조합의 질문도 넣는다.
- 지표: 규격화 정확도, 데이터 포함 재현율·제외 정확도·불가 판정 정확도, 코드 1회 성공률·2회 내 성공률·mock 통과 후 실데이터 실패율, 근거 없는 숫자 비율, 기본 탑재 모듈 + 스냅샷으로 같은 입력에서 같은 중간산출물이 나오는지.
- 지점 기온 추정은 관측소 하나씩 빼는 교차검증으로 평균 절대 오차를 보고한다.

### 테스트하지 않는 것

- React 화면은 자동 테스트 없이 직접 확인한다.

### 선행 사례

- 새 코드베이스라 저장소 안의 선행 테스트는 없다.
- 평가 도구는 InfiAgent-DABench의 "답 형식을 고정해 자동 채점" 방식을, 코드 검증 루프는 Data Interpreter의 "계획 → 코드 → 검증" 방식을 참고한다.

## Out of Scope

- DEM 기반 경사·사면 방향·지형 그림자 일사량 모델링 (90m 해상도 한계, 미반영으로 표시)
- 30m 등 다른 해상도 DEM
- 작업 실패 시 재계획(남은 작업 목록 수정)
- 3회 이상의 코드 재시도, "다른 방법" 시도
- 작업 그래프(DAG). 순서 있는 작업 목록만 지원
- 수익·수확량 예측과 금액 계산
- 추자도 등 부속 섬
- 기상 예보, 실시간 기상, ASOS 자료
- 동해·저온 한계온도(감귤 -7℃, 월동채소 동해 온도 등)에 의한 재배 가능/불가 판정. 신뢰할 만한 1차 자료가 일부 작목에만 있고 의미(피해 개시/치사)도 자료마다 달라서, 극최저기온·저온 일수는 참고 지표로만 보여준다
- 제주시 감귤 생산 데이터 (존재하지 않음)
- 사용자 계정, 로그인, 다중 사용자 동시 실행 관리
- 모바일 전용 화면
- 악의적 코드를 막는 보안 샌드박스
- Jev 등 OpenAI 외 모델
- LangGraph 등 Agent 프레임워크
