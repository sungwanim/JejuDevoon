# 평가 도구 사용법 (티켓 13)

질문 54개를 Runner에 넣어 정답 정보와 비교하고 지표·리포트를 만든다. **도구는 완성됐고, 실제 GPT-4o 실행은 아직 하지 않았다.** 직접 돌려 보면 된다.

## 1. 한 번에 돌리는 순서

프로젝트 루트에서 (PowerShell):

```
# 0) 키 넣기: .env.example을 .env로 복사하고 OPENAI_API_KEY= 뒤에 키를 붙여 넣는다 (키를 채팅·커밋에 올리지 말 것)

# 1) 드라이런: 가짜 LLM, 무료, 약 2분. 도구가 도는지만 본다
.venv\Scripts\python.exe eval\run_eval.py --llm fake --out eval\results\dry

# 2) 소량: 앞 5개만 실제 GPT-4o (약 $0.2~1.4)
.venv\Scripts\python.exe eval\run_eval.py --llm openai --limit 5

# 3) 전체 54개
.venv\Scripts\python.exe eval\run_eval.py --llm openai
```

- 실행 전에 **예상 호출 수와 비용 범위를 출력하고 `계속할까요? [y/N]`을 묻는다.** `--yes`를 주면 묻지 않는다. 입력이 없으면(파이프 등) 중단하고 호출은 0회다.
- 키가 없으면 한국어 안내를 내고 끝난다 (호출 없음).
- 결과는 `eval/results/<타임스탬프>/`(또는 `--out`)에 쌓인다. 이 폴더는 `.gitignore`에 넣어 두었다.

| 옵션 | 뜻 |
|---|---|
| `--llm openai\|fake` | 실제 GPT-4o 또는 드라이런 |
| `--model gpt-4o` | 모델 이름 (비용 계산 단가는 gpt-4o만 있다) |
| `--limit N` / `--ids q01,q05` | 일부만 실행 |
| `--shared-modules` | 질문 사이에 모듈 저장소 공유. 기본은 질문마다 **격리된 임시 폴더**라 먼저 푼 질문이 나중 질문의 재사용을 만들지 않는다. 재사용 효과를 보려면 이 옵션 |
| `--questions PATH` | 다른 질문 파일 |
| `--yes`, `--no-report` | 확인 생략 / 리포트 생략 |

재현성: 호출마다 `temperature=0`, `seed=20261120`(어댑터가 고정). `meta.json`에 질문 파일 해시를 남긴다. 같은 질문 세트로 다시 돌려도 GPT-4o 출력이 완전히 같다는 보장은 없다(OpenAI가 seed를 "최선 노력"으로만 지원).

## 2. 결과 파일

| 파일 | 내용 |
|---|---|
| `results.jsonl` | 질문 하나당 한 줄: 종료 상태, 형식, `needs`, 선택·제외 데이터와 이유 코드, 작업별 코드 시도(분류·단계), 모듈 결정, 미답변, 제거된 문장, LLM 호출 수·토큰·비용(어림)·시간, 예외 |
| `meta.json` | 모델, seed, 시작·종료, 질문 파일 해시, 예상 비용 |
| `traces/<질문 id>/trace.json` | 질문별 Runner 실행 기록(코드 포함)과 결과 HTML |
| `report.md` | 사람이 읽는 리포트 (아래) |

한 질문이 예외로 죽어도 `status: "error"`로 기록하고 다음 질문으로 간다. API 키와 환경변수의 비밀값, `sk-...` 형태의 문자열은 결과·리포트·trace에서 `***`로 바뀐다.

`python eval\report.py eval\results\<폴더>`로 `report.md`를 다시 만들 수 있다 (질문 정답을 고친 뒤 재채점에도 쓴다).

## 3. 리포트 읽는 법 (`report.md`)

1. **지표**: 애매하지 않은 질문(strict) 표. 분모가 0이면 `해당 없음`이다(0%가 아니다).
2. **애매한 질문 지표**: `ambiguous: true` 질문만 따로. 정답 자체가 논쟁거리라 점수보다 불일치 내용을 읽는 용도다.
3. **정답과 다른 질문**: 틀린 항목의 기대/관측, 선택·제외 데이터와 이유 코드, 작업 시도(1회·2회와 실패 분류), 미답변, 안내문. 실패 원인을 짚는 출발점이다. 자세한 건 `traces/<id>/trace.json`.
4. **실패 분류별 집계**: 질문 수준(상태·needs·형식·데이터 선택 등)과 코드 실행 실패 분류(`column_role_mismatch`, `format_error`, `validation_failed` ...).
5. **비용·시간**: 질문당 평균과 합계. 비용은 토큰 x 공개 단가(gpt-4o 입력 $2.50, 출력 $10.00 / 100만 토큰)의 어림값이다. 실제 청구액은 OpenAI 대시보드로 확인.
6. **지점 기온 교차검증 오차**: 관측소 하나씩 빼고 추정한 평균 절대오차. 수집한 실데이터(농업기상 제주 지점)로 계산하며, 관측소가 저지대 위주라 고지대 성능은 알 수 없다.

드라이런 리포트에는 맨 위에 드라이런 경고가 있다. 가짜 LLM은 정답 정보를 보고 답하므로 지표(대부분 100%)는 모델 성능이 아니다.

## 4. 지표 정의

| 지표 | 정의 |
|---|---|
| 규격화 정확도 | 정답이 있는 필요성격(`needs`)·산출물 형식·되묻기 3항목이 모두 맞은 질문 비율. 항목별 정확도도 따로 낸다. `needs`는 정답 파일에 적은 키만 비교한다 |
| 종료 상태 일치율 | 관측 상태 == 기대 상태 |
| 데이터 선택 재현율 | 모든 질문의 `must_include` 합집합 중 실제 선택된 비율(합산 방식) |
| 데이터 제외 정확도 | `must_exclude` 중 선택되지 않은 비율(합산) |
| 불가 판정 정확도 | `infeasible` 여부(상태가 infeasible인가) 일치 |
| 해상도 함정 통과율 | `auxiliary_only` 데이터(도 전체 단위)를 지점 분석의 주 데이터(primary)로 쓰지 않음 |
| 수익 보장 처리율 | 수익 보장을 요구한 질문에서 판정하고 재구성 안내(notice)를 냄 |
| (삭제됨) 합성 경고 정확도 | 앱에서 합성 데이터를 없애 이 지표도 없앴다 |
| 코드 1회 성공률 | 코드 생성·수정까지 간 작업 중 1차 시도 성공. 모듈 재사용만으로 끝난 작업은 분모에서 뺀다 |
| 코드 2회 내 성공률 | 같은 분모에서 작업 성공 |
| mock 통과 후 실데이터 실패율 | 실데이터 단계까지 간 시도 중 실패. **근사**: trace에 "mock 통과"가 따로 없어 `phase == real`인 시도 중 실패를 센다(mock이 `data_problem`이라 실데이터로 넘어간 경우도 섞인다) |
| 모듈 재사용 성공 비율 | 전체 작업 중 재사용으로 성공 |
| 근거 없는 숫자 문장 제거 | HTML을 낸 실행 중 제거된 문장이 있는 비율, 실행당 제거 문장 수. **문장 단위 비율(제거/전체)은 못 낸다** — 전체 문장 수를 기록하지 않는다 |
| 상한 도달 비율 | `limit_hit`(LLM 25회 / 5분)가 있는 실행 비율 |
| 실행 예외 비율 | 도구가 질문을 끝내지 못한 비율. 이 질문은 정답이 있는 항목을 모두 틀린 것으로 센다 |
| 평균 호출·토큰·시간 | 질문당 평균 |

## 5. 질문과 정답을 고치는 법

`eval/questions.jsonl`은 한 줄이 JSON 하나다. 편집기로 직접 고치면 된다.

```json
{"id": "q01", "category": "대표", "question": "...", "click": {"lat": 33.30, "lon": 126.55},
 "expect": {"status": "answered", "output_format": "map",
            "needs": {"point_analysis": true, "time_series": true, "spatial_comparison": false},
            "clarify": false, "in_domain": true,
            "must_include": ["jeju_weather_daily"], "must_exclude": ["seogwipo_citrus_production"],
            "infeasible": false, "profit_guarantee": false,
            "auxiliary_only": ["jeju_vegetable_cultivation"]},
 "ambiguous": false, "note": ""}
```

- `status`: answered / partial / clarify / infeasible. `output_format`, `in_domain`, `needs`는 `null`이면 그 항목은 채점하지 않는다. `needs` 안에서도 적은 키만 채점한다.
- `must_include` / `must_exclude`: 카탈로그 데이터셋 id. `auxiliary_only`(선택): 선택돼도 되지만 보조(auxiliary)로만.
- 결과가 나오는 질문은 `must_include`(반드시 고를 데이터)를 적는다.
- 정답이 애매하면 `"ambiguous": true`로 두고 `note`에 이유를 적는다. 지표가 따로 집계된다.
- 카탈로그가 바뀌면(데이터 추가·교체) `must_include`/`must_exclude`를 다시 봐야 한다.
- `backend/tests/eval/test_eval_questions.py`가 스키마(필수 필드, 데이터셋 id 존재, 30~50개, 유형 분포)를 검사한다. 고친 뒤 `pytest backend/tests/eval`을 돌리면 된다.
- **정답을 시스템 출력에 맞춰 고치지 말 것.** 실제 LLM이 틀릴 수 있어야 평가가 의미 있다. 틀린 게 시스템 규칙 탓이라 정답이 정말 틀렸다고 판단될 때만 고친다.

현재 구성(54개): 대표 10, 처음 보는 조합 11, 도메인 밖 5(데이터 선택에서 불가), 수익 보장 3, 범위 밖 좌표 3, 되묻기 4, 해상도 함정 3, 데이터 없음 6, 관계 타당성 5, 새 도메인 4. 애매한 정답 14개(`q06 q07 q14 q19 q27 q28 q37 q38 q39 q41 q44 q47 q50 q54`).

## 6. 재현성 검사

```
.venv\Scripts\python.exe eval\repro_check.py --n 4
```

verified 모듈과 스냅샷만으로 끝나는 질문을 골라 가짜 LLM으로 **같은 입력을 두 번**(질문마다 새 모듈 저장소) 실행해 중간산출물(표·dict)의 해시가 같은지 본다. LLM 호출이 정해져 있어 비용이 없다. LLM 자체의 변동성은 보지 않는다. 그건 실제 평가를 두 번 돌려 `results.jsonl`을 비교해야 한다.

## 7. 비용 안내

| 범위 | 호출 수(어림) | 비용(어림) |
|---|---|---|
| `--limit 5` | 25~70회 | $0.2 ~ 1.4 |
| 전체 54개 | 197~485회 | $1.6 ~ 9.9 (약 2,200~13,900원) |

질문의 기대 경로로 계산한 범위다. 낮은 쪽은 verified 모듈 재사용, 높은 쪽은 코드 생성·수정이 섞였을 때. 질문 한 개는 호출 25회 상한이 있다. 정확한 값은 첫 실행 뒤 `report.md` 5절에서 보라. 단가는 공개 가격을 옮긴 것이라 바뀔 수 있다.

## 8. 알려진 한계

- **실제 GPT-4o로 실행한 적이 없다.** 질문·정답·지표 정의는 현재 시스템 규칙(spec, `selection.py`, `request_plan.py`)을 읽고 정했다. 첫 실행에서 정답 쪽이 틀린 곳이 나올 수 있다.
- 드라이런의 가짜 LLM은 정답을 보고 답한다. 도구 검증용이지 시스템 성능이 아니다.
- 교차검증 오차는 농업기상 제주 16개 지점(고도 18~208m) 기준이다. 고지대는 알 수 없다.
- 데이터 문의 질문(`q06`, `q07`)은 전용 경로가 없어 관련 데이터 선택 여부만 본다(애매로 표시).
- 근거 없는 숫자 문장 제거는 "전체 문장 수 대비 비율"이 아니라 실행 단위로만 낸다. mock 통과 후 실패율은 근사다.
- 비용은 토큰 x 공개 단가의 어림값이다. 같은 질문 세트를 다시 돌려도 GPT-4o 출력은 조금 달라질 수 있다.
- 질문은 순차 실행이다. 전체 실행에 질문당 수 초~수십 초가 걸린다(코드 격리 실행 포함).
