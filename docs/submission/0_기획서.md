# 제주 공공데이터 분석 AI Agent 기획서

여러 도메인의 제주 공공데이터를 질문 한 번으로 탐색하고, 데이터 구조에 맞는 분석 코드를 Agent가 직접 작성해 결과를 설명하는 로컬 서비스

## 1. 구현목표

제주데이터허브와 제주빅데이터센터를 비롯한 공공데이터는 농업, 기상, 환경, 도시 등 영역별로 흩어져 있고, 제공 형식도 API와 CSV, 인코딩과 단위, 시간과 공간의 해상도까지 제각각이다. 도민이 "제주공항 근처에서 소음이 가장 큰 곳은 어디인가", "작년에 비가 가장 많이 온 달은 언제인가"처럼 일상적인 질문의 답을 얻으려 해도, 어떤 데이터가 있는지 찾고 구조를 파악해 직접 계산하는 일은 데이터 전문가가 아니면 넘기 어려운 벽이다. 이 프로젝트의 분석 주제는 바로 이 벽을 없애는 것이다. 도민이 평소 말투로 질문하면 Agent가 데이터 탐색, 데이터 선택, 분석, 결과 설명을 대신하는 "도민을 위한 제주 공공데이터 분석 Agent"를 만든다.

AI를 활용한 데이터 분석의 목표는 세 가지다. 첫째는 탐색의 자동화다. Agent는 등록된 데이터 목록(카탈로그)을 읽고 질문에 필요한 데이터를 고르며, 고르지 않은 데이터에는 기간이나 지역, 공간 단위가 맞지 않는다는 식의 이유를 남긴다. 둘째는 분석 코드의 자동 작성이다. Agent는 원본 전체가 아니라 컬럼 이름과 단위, 통계, 샘플 값 같은 데이터의 구조만 보고 분석 코드를 직접 작성하고, 모의 데이터와 실제 데이터로 검증한 뒤, 통과한 코드는 모듈로 저장해 다음 질문에서 재사용한다. 셋째는 설명이다. 결과는 보고서, 그림, 지도 가운데 질문의 성격에 맞는 형식의 HTML 한 장으로 만들고, 사용한 데이터와 제외한 데이터, 계산 근거와 한계를 함께 보여 준다.

이 Agent의 가장 큰 특징은 특정 도메인에 묶이지 않는다는 점이다. 농업 데이터만 다루도록 만든 분석 프로그램이라면 새 데이터가 들어올 때마다 사람이 분석 코드를 새로 짜야 한다. 이 Agent는 새 데이터를 카탈로그에 항목으로 등록하기만 하면 같은 흐름으로 질문을 받고 코드를 작성한다. 현재는 농업(농산물 거래 통계와 이동평균, 서귀포시 감귤 생산, 채소 재배현황), 기상(농업기상 관측소 일자료), 환경(제주공항 항공기 소음, 환경소음), 도시(도시숲 조성사업)의 여덟 가지 데이터를 등록해 도메인을 가로지르는 동작을 보여 준다. 분석 과정에서 Agent가 어떤 판단을 했는지 사용자에게 단계별로 보여 주고, 판단 근거가 없는 것은 판정하지 않는다는 원칙도 함께 구현 목표에 둔다. 재배 적합도나 수익은 근거 데이터가 없어 판정하지 않고, 수익을 보장하지도 않는다.

## 2. 서비스 제안

이 서비스는 센터 PC에서 한 사람이 쓰는 로컬 웹앱이다. 사용자는 브라우저에서 제주 지도와 입력창을 보며 질문한다. 활용하는 데이터는 제주데이터허브의 농산물 품종별 일일 거래 통계와 거래 이동평균, 서귀포시 감귤 생산 정보, 제주채소류재배현황을 필수 데이터로 삼고, 여기에 공공데이터포털의 농업기상 관측 일자료, 제주공항 항공기 소음, 도시숲 조성사업, 환경소음 측정결과, 국토지리정보원의 90미터 고도 자료(DEM)를 더한다. 같은 질문 틀에서 농업, 기상, 환경, 도시 데이터를 오가며 답할 수 있다는 점이 서비스의 핵심이다.

핵심 기능은 다음과 같다. 사용자는 질문을 글로 쓰거나, 특정 장소가 궁금하면 지도에서 위치를 클릭해 "여기"라고 묻는다. 위치가 필요한데 클릭이 없으면 Agent가 한 번 되묻고, 답하면 이어서 분석한다. Agent는 질문에 필요한 데이터를 고르면서 고른 이유와 제외한 이유를 남기고, 서로 다른 두 데이터의 관계를 묻는 질문이면 의미상 연결할 근거가 있는지도 따진다. 주식 가격과 재배면적처럼 연결할 이유가 없거나 카탈로그에 맞는 데이터가 없는 질문은 억지로 계산하지 않고 이유와 함께 불가로 답한다. 데이터가 정해지면 Agent가 분석 작업을 나누고, 작업마다 저장소에 검증된 모듈이 있으면 재사용하고 없으면 새 코드를 작성하며, 코드는 정적 검사와 모의 데이터 실행, 실제 데이터 실행을 거쳐 검증한다. 실패하면 원인을 분류해 한 번만 고쳐 다시 시도하고, 그래도 실패하면 그 작업은 실패로 표시한다. 결과 문서의 요약 문장에 든 숫자는 계산 결과와 대조해 근거가 없으면 문장을 지운다. 이 모든 과정은 화면의 "생각 과정" 패널에 요청을 어떻게 이해했는지, 어떤 데이터를 왜 골랐는지, 작업을 어떻게 나눴는지, 모듈을 재사용했는지 새로 만들었는지, 검증이 통과했는지가 쉬운 말로 한 줄씩 쌓인다.

편의성 면에서는 설치와 실행의 문턱을 낮추는 데 집중했다. 화면은 미리 만들어 두었기 때문에 센터 PC에는 파이썬만 있으면 되고, 실행 파일 하나를 더블클릭하면 서버가 켜지고 브라우저가 열린다. 사용자는 명령어를 입력할 필요가 없고, 결과는 HTML 파일 한 장으로 저장해 다른 사람에게 전달할 수 있다. 결과마다 사용 데이터, 제외 이유, 분석 과정, 한계, 출처와 이용조건이 자동으로 붙어 읽는 사람이 결과를 어디까지 믿어야 하는지 스스로 판단할 수 있다.

분석 데이터의 활용 방안은 센터가 쓰는 입구를 생각해 정했다. 센터에 새 데이터가 생기면 메타 정보를 담은 항목 하나를 등록하는 것으로 도민이 질문으로 탐색할 수 있는 창구가 된다. 사람이 검토한 분석 코드를 모듈로 등록해 두면 같은 종류의 질문에 코드를 새로 만들지 않고 재사용해 결과가 안정되고 호출 비용도 줄어든다. 실행 기록이 질문마다 남아 있어 센터가 어떤 질문에 어떤 데이터와 코드가 쓰였는지 사후에 점검할 수 있고, 수집한 데이터는 한 줄의 수집 명령으로 갱신한다.

## 3. Agent 개발 구성

참여자는 참가자 1인이다. 기획과 데이터 정리, 개발, 검증을 모두 맡았고, 개발 과정에서는 AI 코딩 도구의 도움을 받았다. 사용한 개발용 AI 모델은 Claude Opus 5.5와 Claude Sonnet 5.5이고, 이를 쓰는 도구는 Claude Code다. 요구사항과 데이터 원칙, 범위는 사람이 정하고 결과를 직접 실행해 검토했다. 이 개발용 AI는 서비스가 실행 중에 호출하는 모델이 아니다. 서비스 목표는 비전문가인 도민이 질문만으로 데이터 분석 결과를 얻는 것이고, 개발의 목표는 이를 센터 PC 한 대에서 별도 서버 없이 돌아가는 형태로 만드는 것이다.

Agent의 흐름은 프레임워크를 쓰지 않고 파이썬 상태 머신으로 구현한 다섯 단계다. 첫 단계는 요청 규격화로, 질문과 지도 좌표를 받아 목표와 하위 질문, 필요한 분석의 성격, 위치, 빠진 정보를 구조화한다. 좌표가 제주 본섬 밖이면 불가로 끝내고 위치가 빠졌으면 되묻는 규칙은 코드가 적용한다. 둘째 단계는 데이터 선택으로, 카탈로그 요약을 보고 쓸 데이터와 제외 이유를 고른다. 이어 기간과 지역, 컬럼, 공간 단위가 맞지 않으면 규칙이 선택을 바로잡는다. 셋째 단계는 로드와 요약으로, 선택한 데이터를 읽고 컬럼별 통계 요약을 만든다. 지점 질문이면 이때 지도에서 고른 위치의 고도를 지형 자료에서 읽어 입력에 더한다. 넷째 단계는 분석으로, 작업 목록을 짜고 작업마다 모듈 재사용, 수정, 신규 작성 중 하나를 정해 코드를 검증하며 실행한다. 마지막 단계는 렌더로, 계산된 결과만을 근거로 보고서 구성을 설계하고 숫자 근거 대조를 거쳐 보고서, 그림, 지도 중 하나의 형식으로 HTML을 만든다. 질문이 공간 정보를 필요로 하면 지도 형식이 고정된다.

실행 중에 쓰는 모델은 OpenAI의 GPT-4o 하나다. 모든 호출은 온도 0과 고정된 시드, 구조화된 출력(JSON 스키마)으로 설정해 결과의 변동을 줄였다. 이 모델이 하는 일은 요청 규격화, 데이터 선택과 관계 판단, 분석 작업 계획과 코드 작성, 모듈 재사용 결정, 보고서 구성이다. 계산과 데이터 로드, 상태 전이, 상한 관리는 모델이 아니라 일반 파이썬 코드가 한다. Agent가 쓰는 도구와 API는 다음과 같다. 날짜와 숫자 변환, 지역 필터, 조인 같은 고정 도구가 있고, 생성된 코드를 별도 프로세스에서 허용된 라이브러리(pandas, numpy, scipy, 표준 라이브러리)만으로 시간 제한을 두고 실행하는 실행기가 있다. 분석 모듈 저장소는 검증 상태로 등록해 둔 시드 모듈 네 개(사람의 검토 기록은 아직 없다)와 자동으로 저장된 모듈을 글자 유사도로 검색한다. 외부로는 제주데이터허브 API와 공공데이터포털의 농업기상 API로 데이터를 수집하고, OpenAI API로 모델을 호출한다.

판단과 자율 수행의 범위는 명확히 나눴다. Agent가 스스로 판단하는 것은 어떤 데이터를 쓸지, 분석을 어떻게 나눌지, 어떤 코드를 짤지, 저장된 모듈을 재사용할지, 결과를 어떤 구성으로 보여줄지다. 반대로 코드가 정하는 것은 제주 본섬 범위 검사, 선택 결과의 규칙 교정, 한 번의 실행에서 모델 호출 25회와 5분, 작업당 코드 시도 2회, 코드 한 번 실행 60초라는 상한, 코드 검증 통과 여부, 숫자 근거 대조다. 재계획은 하지 않는다. 사용자는 위치가 필요할 때만 개입한다. Agent는 재배 적합도나 한계온도를 판정하지 않고 수익을 보장하지 않으며, 근거가 없는 질문에는 답하지 않고 이유를 말한다. 생성된 코드는 허용된 라이브러리만 쓰도록 정적 검사를 거치고, 별도 프로세스에서 시간 제한과 키 차단을 둔 채 실행하며, 서비스는 센터 PC에서 한 사람이 로컬로 쓰는 것을 전제로 설계했다.

## 4. 데이터 활용 계획

필수 데이터로는 제주데이터허브의 데이터 네 가지를 쓴다. 농산물 품종별 일일 거래 통계는 허브 API로 수집해 품종별 가격 추세와 변동성을 분석하는 데 쓰고, 거래 이동평균은 같은 방식으로 수집해 가격의 이동평균에 관한 질문에 쓴다. 서귀포시 감귤 생산 정보는 읍면동별 농가수, 면적, 생산량을 담은 CSV로 읍면동별 비교와 연도별 추세에 쓰며 제주시 자료는 없다. 제주채소류재배현황은 연산과 작목별 면적, 생산량, 조수입을 담은 CSV로 작목별 면적당 조수입과 재배면적 추이에 쓰고, 비용이 없으므로 조수입 기준으로만 해석한다. 이 가운데 거래 통계와 이동평균은 2024년 1월부터 2025년 12월까지 수집했다.

여기에 도메인을 넓히는 데이터를 더한다. 공공데이터포털의 농촌진흥청 농업기상 API에서 제주 관측소 열여섯 곳의 2024년 일 기온과 강수량을 위경도, 고도와 함께 수집해 지점 기후 분석과 기상 질문에 쓴다. 제주공항 항공기 소음은 측정소 열세 곳의 분기별 소음도(2010년부터 2023년까지)를 담은 CSV이고, 도시숲 조성사업은 2007년부터 2021년까지 사업 위치와 사업량을 담은 CSV, 환경소음은 2024년 분기별 서른다섯 개 지점의 시간대별 소음도를 담은 CSV다. 국토지리정보원의 90미터 고도 자료는 지도에서 고른 지점의 고도와 바다·육지 판정에만 쓴다.

수집과 전처리는 같은 틀로 처리한다. 데이터마다 출처, 단위, 기간, 컬럼의 이름과 의미, 읽는 규칙을 적은 카탈로그 항목을 두고, 로더가 이 규칙으로 파일을 읽는다. 로더는 한글 인코딩을 자동으로 판별하고, 문자열로 오는 숫자를 숫자로 바꾸며, 이동평균의 0.00이나 소음 데이터의 빈 값과 대시처럼 결측을 뜻하는 표기를 결측으로 바꾼다. 전국 공항 자료에서는 제주공항만 남기고, 환경소음의 평면 좌표는 위경도로 변환한다. 이 좌표 변환은 알려진 위치와의 대조로 정한 추정이라 오차가 약 1킬로미터일 수 있음을 결과에 밝힌다. API 데이터는 수집한 뒤 파일 스냅샷으로 고정해 같은 질문이 같은 데이터로 계산되게 하고, 수집이 한도나 오류로 멈추면 이어받는다. 수집 과정에서 센서 오류로 보이는 값은 걸러낸다. 실제로 일 최저기온 영하 33도 값이 있어 상식 범위를 벗어난 날을 제외했다. 분석 전에는 컬럼별 결측률과 범위, 샘플을 요약한 정보를 만들어 모델이 데이터 원본 대신 이 요약만 보고 코드를 짜게 한다.

이용조건은 데이터별로 정리해 결과 화면에 출처와 함께 표시한다. 허브 데이터는 허브 이용약관을 따른다. 농업기상 관측 자료는 공공누리 제4유형(출처표시, 상업적 이용금지, 변경금지)으로 안내되어 있고, 이 프로젝트의 가공과 분석 사용은 가능하다고 확인했다. 그 밖의 데이터도 제공처와 이용조건을 데이터별로 정리해 결과 화면에 함께 표시하며, 세부 조건은 센터와 확인해 반영한다. 데이터에는 개인정보와 금융정보가 없고, 사용자가 입력한 질문 문장은 그대로 OpenAI로 전송되므로 개인정보를 쓰지 않도록 안내한다.

## 5. 개발·탑재 계획

구현 범위는 질문 입력부터 결과 HTML과 실행 기록 저장까지 다섯 단계 전체 흐름이다. 데이터 카탈로그 여덟 가지와 수집 명령, 시드 모듈 네 개(검토 기록은 아직 없다)와 자동 저장 모듈 저장소, 생성 코드 실행기, 지점 고도 조회와 지점 기후 추정, 보고서 렌더, 지도와 입력창과 생각 과정을 갖춘 화면이 구현되어 있다. 구현된 흐름은 가짜 모델을 쓰는 자동 테스트로 단계별 동작을 확인했고, 실제 GPT-4o로도 평가용 질문을 실행해 보았다. 단순한 질문에서는 원자료와 일치하는 답이 나오는 것을 확인했고, 질문과 맞지 않는 요청이 이유와 함께 걸러지는 것도 확인했다. 여러 작업을 이어야 하거나 두 데이터를 합쳐야 하는 복잡한 질문은 이 Agent가 가장 큰 가치를 내는 영역이자 고도화 단계의 핵심 과제다. 코드 생성 프롬프트를 다듬고, 검증을 통과한 모듈을 계속 쌓아 재사용률을 높이며, 평가용 질문 세트를 일괄 실행해 정량 지표로 개선 효과를 확인하는 순서로 안정성을 높일 계획이다. 기온 관측소가 저지대에 있어 한라산 고지대 값은 고도로 보정한 추정이라는 점은 결과에 표시해 해석 기준을 함께 제공한다.

기술 환경은 윈도우에서 파이썬 3.14, 백엔드는 FastAPI와 uvicorn, 데이터 처리는 pandas와 numpy, scipy, 고도 자료는 rasterio와 pyproj를 쓴다. 화면은 리액트 19와 Vite, Leaflet으로 만들어 미리 빌드해 두었고, 백엔드가 같은 포트로 서빙하므로 실행에 Node는 필요하지 않다. 서버는 로컬 주소에만 열리고, 환경변수 파일에 둔 API 키는 코드와 제출물에 포함되지 않는다.

화면은 위에서 아래로 구성된다. 제주 지도, 질문 입력창, 다섯 단계의 진행 표시줄, 생각 과정 패널, 결과 문서가 이어지고, 결과 아래에 사용한 데이터와 제외한 데이터와 이유를 보여 주는 패널, 전문가용 실행 기록 패널이 있다. 결과 문서는 한 장의 HTML로 저장할 수 있다.

센터 실행환경은 운영 PC 최소사양(Intel Core i7-8700, GTX 1060, RAM 32GB)을 기준으로 잡았다. 이 서비스는 GPU를 쓰지 않는다. 모델 추론은 외부 서버에서 하고 로컬에서는 수천에서 수만 행 규모의 표를 다루기 때문에 사양은 충분할 것으로 보지만, 센터 사양을 기준으로 설계했고, 실제 사양의 PC에서 실측해 최적화하는 일은 탑재 단계에서 진행할 계획이다. 센터 PC에는 파이썬 3.14와 필요한 라이브러리 설치, 환경변수 파일 설정이 필요하다. 질문 하나를 처리하는 데는 대략 20초에서 60초가 걸렸다.

외부 서비스 의존성은 분명히 밝힌다. 가장 큰 의존은 OpenAI API다. 서비스가 동작하려면 인터넷과 OpenAI API 키가 필요하고, 실제로 돌린 질문 한 건의 호출 비용은 약 30원에서 130원이었다. API 키와 호출 비용은 센터의 운영 방식에 맞춰 협의해 정한다. 제주데이터허브와 공공데이터포털은 데이터를 수집하거나 갱신할 때만 필요하고, 수집한 스냅샷이 있으면 평소 질문에는 호출하지 않는다. 지도 배경 타일과 결과 화면의 차트, 흐름도, 지도 라이브러리는 외부 CDN에서 불러오므로 인터넷이 막히면 차트는 표로, 지도는 좌표 표로, 흐름도는 번호 목록으로 대체된다. 외부 서비스 의존을 줄이는 방안으로는 라이브러리를 로컬에 포함하는 것과, 센터가 허용하는 LLM 환경이 생기면 모델 어댑터만 교체하는 것을 검토할 수 있다. 어댑터가 모델 호출을 한곳에 모아 두어 교체 범위가 작다.
